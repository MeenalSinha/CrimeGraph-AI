# CrimeGraph AI -- Architecture & Data Model

This document was missing entirely in earlier passes of this build (flagged as
a real gap in the checklist audit). It covers system architecture and the
data model actually implemented -- not an aspirational target architecture.

## System architecture

```mermaid
flowchart LR
    subgraph Client
        WEB["Next.js Web Dashboard<br/>(13 routes, App Router)"]
        MOB["Expo / React Native<br/>Mobile Companion"]
    end

    subgraph Backend["FastAPI Backend (single process)"]
        MW["Middleware:<br/>CORS -> RateLimit -> SecurityHeaders -> RequestLogging"]
        API["REST Routers<br/>(auth, dashboard, prediction, network,<br/>patrol, investigations, alerts, search,<br/>chat, scenario, reports, analytics)"]
        SVC["Service Layer<br/>(risk, graph, patrol, investigation,<br/>alerts, entity_resolution, search,<br/>chat, scenario, report, analytics, auth)"]
        DATA["Data Access Layer<br/>(app/data/store.py)"]
    end

    subgraph Storage["In-Process Storage (no external DB -- see AUDIT.md)"]
        CSV["Generated CSVs<br/>(persons, firs, vehicles, phones,<br/>accounts, calls, transfers, associations)"]
        MODELS["Trained ML artifacts<br/>(XGBoost x3, IsolationForest,<br/>joblib-serialized)"]
        GRAPH["In-memory NetworkX Graph<br/>(~4,600 nodes)"]
    end

    WEB -->|HTTPS/JSON| MW
    MOB -->|HTTPS/JSON, AsyncStorage cache| MW
    MW --> API --> SVC --> DATA
    DATA <--> CSV
    SVC <--> MODELS
    SVC <--> GRAPH
```

**Why no Postgres/Redis/Neo4j box in this diagram:** this prototype deliberately
runs as a single FastAPI process with in-memory pandas DataFrames and a
NetworkX graph, generated fresh (deterministically, via a fixed seed) on
first boot. See `AUDIT.md` for the reasoning and the swap-in points
(`app/data/store.py` for a real database, `app/services/graph_service.py`
for Neo4j) if this were to become a real multi-user deployment.

## Request flow (example: a prediction request)

```mermaid
sequenceDiagram
    participant U as Officer (browser)
    participant N as Next.js page
    participant M as FastAPI middleware
    participant R as prediction router
    participant S as risk_service
    participant X as XGBoost models (joblib)

    U->>N: Move hour/weekday sliders, set weather
    N->>M: POST /api/prediction/risk
    M->>M: rate limit check, security headers,<br/>structured log
    M->>R: validated PredictionRequest<br/>(pydantic bounds: hour 0-23, weekday 0-6)
    R->>S: predict_risk(ward, hour, weekday, weather, festival)
    S->>X: count_model.predict(), severity_model.predict(),<br/>type_model.predict_proba()
    X-->>S: expected_count, expected_severity, crime-type probabilities
    S->>S: compute risk_score, risk_band, confidence,<br/>build explanation.reasons[]
    S-->>R: full response dict
    R-->>N: JSON
    N-->>U: risk score, band, explanation, likely crime types
```

## Data model (entity relationships)

```mermaid
erDiagram
    PERSON ||--o{ VEHICLE : owns
    PERSON ||--o{ PHONE : owns
    PERSON ||--o{ ACCOUNT : owns
    PERSON ||--o{ FIR : "suspected_in"
    PERSON }o--o{ PERSON : "associate / known_contact"
    PHONE }o--o{ PHONE : "called (aggregated to person-person edge)"
    ACCOUNT }o--o{ ACCOUNT : "transferred (aggregated to person-person edge)"
    FIR }o--|| STATION : "handled_by"

    PERSON {
        string person_id PK
        string name
        int age
        string gender
        string ward
        string aliases
        bool is_person_of_interest
        float risk_score
        string gang_affiliation
    }
    FIR {
        string fir_id PK
        string crime_type
        int severity
        string ward
        float lat
        float lng
        datetime timestamp
        string weather
        bool is_festival_day
        int population_density
        string weapon
        string suspect_id FK
        string station_id FK
        string status
    }
    VEHICLE {
        string vehicle_id PK
        string plate
        string type
        string owner_id FK
    }
    PHONE {
        string phone_id PK
        string number
        string owner_id FK
    }
    ACCOUNT {
        string account_id PK
        string bank
        string owner_id FK
    }
    STATION {
        string station_id PK
        string name
        string ward
        int officer_count
        int vehicle_count
    }
```

This is the schema actually generated by `app/data/synthetic_generator.py` and
loaded by `app/data/store.py` -- not a target schema for a future database.
If this became a real Postgres deployment, each table above maps directly to
a Postgres table with the same columns; `PERSON`-to-`PERSON` edges (calls,
transfers, associations) would become either a join table or, more naturally,
live in a graph database (Neo4j) alongside the rest of the relationship graph.
